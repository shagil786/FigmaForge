The module is a cohesive runtime kernel organized around a central `PipelineCoordinator` (`pipeline.ts`) that drives a fixed ordered sequence of stages defined in `types.ts` (`PIPELINE_STAGES`: ingest → normalize → resolve → layout → generate → assets → render → compare → repair → verify). Each stage is a pure `StageHandler(ctx, input)` function registered via `onStage`, receiving a shared `PipelineContext` that composes cross-cutting concerns: an append-only `EventLog` (`events.ts`), a `CheckpointManager` (`checkpoint.ts`) persisting per-stage JSON checkpoints under `<outputDir>/<runId>/checkpoints/`, an `ArtifactStore` (`artifacts.ts`) providing content-addressed storage keyed by SHA-256 hashes, a `BudgetTracker` (`budget.ts`) enforcing token/time/iteration limits, and a `security` bundle (`PathSandbox`, `SecretGuard`, `ShellGuard`, `AssetValidator`, `ApprovalGate`) from `security.ts`. A `StateMachine` (`state.ts`) enforces strict run lifecycle transitions (pending → running → paused/completed/failed/cancelled/rolled_back) and coordinates checkpoint save/load for resumability. Cross-cutting primitives include `withRetry`/`withTimeout` (`retry.ts`) for exponential-backoff retries with `AbortSignal` cancellation, and a typed `ToolRegistry` (`tools.ts`) with a built-in `createPythonTool` bridge to spawn `python3` scripts from the plugin directory. The module exposes a flat barrel export via `index.ts`; types are intentionally pure data and JSON-serializable so they survive checkpoint persistence. Dependency direction is one-way: `pipeline.ts` depends on all other modules; `state.ts` depends on events/checkpoint/types; `tools.ts` and `security.ts` have no internal dependencies beyond `types.js`.
