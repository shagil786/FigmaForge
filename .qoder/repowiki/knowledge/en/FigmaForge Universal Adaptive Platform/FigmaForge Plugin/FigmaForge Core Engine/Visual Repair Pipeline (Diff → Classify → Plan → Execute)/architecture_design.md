The module implements a staged pipeline orchestrated by `RepairLoop.run()`, which drives the cycle: Render → Diff (`DiffEngine.diff`) → Classify (`RepairClassifier.classify` on `DiffReport.mismatches`) → Plan (`PatchPlanner.plan` producing an ordered `PatchPlan`) → Execute (`PatchExecutor.execute` mutating in-memory tokens, styles, layout plans, IR assets) → Re-render. Each stage is a self-contained class with explicit dependencies injected via constructor or parameters; there are no global singletons. Data flows through immutable dataclasses: `DiffReport` → `ClassificationReport` → `PatchPlan` → `ExecutionResult`, each exposing `to_dict()` for JSON serialization. The planner enforces a fixed strategy priority (`CATEGORY_MISSING_ELEMENT` → `EXTRA_ELEMENT` → `GEOMETRY` → `SPACING` → `TOKEN` → `TYPOGRAPHY` → `ASSET` → `COLOR` → `RESPONSIVE`) and groups shared-token candidates so one token patch resolves multiple mismatches. The executor dispatches per-`target_type` (`token`, `style`, `layout`, `position`, `asset`, `structure`) to dedicated `_apply_*_patch` methods and records every mutation as a `MutationRecord` enabling reverse-order `rollback()`. `RepairHistory` is append-only, persisting each iteration's diff/classification/plan/execution plus screenshot paths, and supports `get_rollback_state(target_iteration)` for replay. The loop injects external concerns via `RenderCallable` and `ApprovalCallable` protocols, keeping the core free of browser/Playwright coupling.
